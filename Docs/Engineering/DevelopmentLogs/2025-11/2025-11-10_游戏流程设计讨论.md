# 游戏流程设计讨论 - Session生命周期与三种模式统一架构

日期：2025-11-10
负责人：用户 + AI
状态：已完成

---

## 背景

在角色切换功能的文档整合阶段，发现之前添加的游戏流程设计（MainMenu → Home → Lobby → Gameplay）存在以下问题：

1. **可能过度设计**：引入了GameFlowSubsystem，可能不必要
2. **Session生命周期不清晰**：未考虑DestroySession、ReturnToMainMenu的技术限制
3. **模式设计不明确**：三种游戏模式（单人、分屏、在线）的流程和交互未统一
4. **家园（Hub）联机冲突**：如果允许联机进入家园，"另一个主角"的逻辑会混乱

因此，需要重新设计完整的游戏流程架构，确保技术可行且逻辑清晰。

---

## 关键技术调研

### 1. Session生命周期

通过搜索UE官方文档和社区讨论，确认以下机制：

**CreateSession → StartSession → JoinSession → EndSession → DestroySession**

- 所有Session操作都是异步的，必须等待OnComplete委托
- Host调用DestroySession会通知所有客户端断开连接
- Client调用DestroySession只影响本地Session状态
- 如果不DestroySession，下次CreateSession/JoinSession会失败

**ReturnToMainMenu实现：**
```cpp
void UGameInstance::ReturnToMainMenu()
{
    // 调用 HandleDisconnect（在 OnlineSession 或 Engine 上）
    // 触发 Hard Travel 回到项目设置的 Default Map
}
```

**关键发现：**
- ReturnToMainMenu触发Hard Travel，不是Seamless Travel
- Hard Travel会重建PlayerController、PlayerState、Character、ASC等所有对象
- 这意味着返回主菜单后，所有游戏内状态都会丢失

**技术限制：**
- 离开Lobby后必须回到MainMenu（无法像艾尔登法环那样回到Hub）
- 但副本完成后可以ServerTravel回Lobby（保持Session）

### 2. Seamless Travel vs Hard Travel

| 对象 | Seamless Travel | Hard Travel |
|------|----------------|-------------|
| PlayerController | 保留 | 重建 |
| PlayerState | 保留（通过CopyProperties） | 重建 |
| ASC (在PlayerState上) | 保留 | 重建 |
| Character/Pawn | 重建 | 重建 |
| GameMode | 重建 | 重建 |

**结论：**
- MainMenu ↔ Hub ↔ Dungeon之间使用Seamless Travel，ASC可以持久化
- 离开游戏（DestroySession + ReturnToMainMenu）使用Hard Travel

### 3. 单人/分屏/在线的统一架构

**关键发现：**
- UE的联机代码可以用在单机上（Listen Server架构）
- 单人模式 = Listen Server（无其他玩家加入）
- 本地分屏 = Listen Server（多个本地PlayerController）
- 在线模式 = Listen Server（远程玩家通过Session加入）

**优势：**
- 代码复用率高
- 逻辑一致性强
- 不需要维护两套代码（单机 vs 联机）

## 设计决策

### 决策1：MainMenu不分三种模式入口

**问题：** 是否在MainMenu分"单人游戏"、"本地分屏"、"在线联机"三个入口？

**结论：** 不分，使用统一入口。

**原因：**
1. 本地分屏本质上是在进入副本时CreateLocalPlayer，不是在MainMenu创建
2. UE的联机代码可以用在单机上，不需要区分代码路径
3. 玩家在选择副本后再决定游戏模式，灵活性更高

**MainMenu结构：**
```
MainMenu
├── 新游戏（创建存档）
├── 继续游戏（存档列表）
├── 角色定制（需要先选择存档）
├── 设置
└── 退出
```

### 决策2：家园（Hub）是单机专属

**问题：** 在线模式能否进入家园？

**结论：** 不能，家园是单机模式专属。

**原因：**
1. 家园中的"另一个主角"是本地存档中的另一个性别角色
2. 如果在线模式允许进家园，其他玩家会看到你的"另一个主角"，逻辑混乱
3. 本地分屏也不能进家园（2个玩家，2个存档，哪个存档的"另一个主角"出现？）

**家园功能：**
- 自由探索（游泳、瑜伽、摆pose）
- 与另一个主角互动（AI控制，存档中另一个性别角色）
- 切换角色（单人模式专属）
- 购买武器、升级技能
- 选择副本

### 决策3：Lobby必须是Level，不是Widget

**问题：** 在线模式的匹配大厅应该是Widget还是Level？

**结论：** 必须是Level。

**原因：**
1. 副本完成后需要ServerTravel回Lobby，目标必须是一个Map
2. 如果用Widget，副本完成后只能回MainMenu，无法"保持Session继续组队"
3. Lobby Level可以保持Session存活，玩家在Lobby中可以自由离开/加入
4. Lobby是一个3D场景，玩家可以看到队友的角色、装备，比纯UI更有沉浸感

**Lobby Level设计：**
- 一个小的封闭空间（电梯、飞机内部、作战指挥室）
- 2-4个玩家站位
- 中间有全息投影显示副本信息
- 墙上有武器架、装备展示

### 决策4：副本准备界面 - 动态模式选择

**问题：** 玩家如何选择游戏模式（单人/分屏/在线）？

**结论：** 在Hub选择副本后，弹出副本准备界面，提供三个选项。

**界面设计：**
```
┌─────────────────────────────────────┐
│     副本准备界面                      │
│                                     │
│  副本名称: [第一章 - 觉醒]           │
│  预计时长: 30-45分钟                 │
│  推荐等级: 5级                       │
│                                     │
│  ┌─────────┐  ┌─────────┐  ┌─────────┐│
│  │单人开始  │  │添加本地  │  │在线匹配│ │
│  │         │  │玩家      │  │        │ │
│  └─────────┘  └─────────┘  └─────────┘│
│                                     │
│              [返回]                  │
└─────────────────────────────────────┘
```

**行为：**
- 单人开始：直接ServerTravel进副本（AI队友已在Hub生成）
- 添加本地玩家：CreateLocalPlayer(1) → 玩家2选择存档 → ServerTravel进副本
- 在线匹配：显示"创建房间/加入房间" → CreateSession/JoinSession → ServerTravel到Lobby Level

### 决策5：副本完成后的流程

**问题：** 副本完成后应该回哪里？

**结论：**
- 单人/分屏：ReturnToMainMenu（DestroySession不适用单机）
- 在线模式：ServerTravel回Lobby（Session保持），玩家可选择继续或离开

**在线模式流程：**
```
Dungeon完成
  ↓
ServerTravel回Lobby（Session保持）
  ↓
玩家选择：
  1. 继续组队 → Host选择下一个副本 → 再次ServerTravel到Dungeon
  2. 离开队伍（Client） → DestroySession → ReturnToMainMenu
  3. 解散队伍（Host） → 通知所有客户端 → DestroySession → ReturnToMainMenu
```

### 决策6：副本解锁方案 - 个人解锁 + 允许跳关

**问题：** 如何管理副本解锁进度？

**结论：** 方案B - 个人解锁 + 允许跳关。

**逻辑：**
- 每个玩家有独立的副本解锁进度
- Host可以选择自己已解锁的任何副本
- Client如果副本未解锁，弹出警告："此副本尚未解锁，完成后将标记为'辅助完成'而非'首次完成'，是否继续？"
- 跳关完成不会获得首次通关奖励，但可以标记为"辅助完成"

**存档结构：**
```cpp
USTRUCT(BlueprintType)
struct FDungeonProgress
{
    GENERATED_BODY()

    UPROPERTY(SaveGame)
    FName DungeonID;

    UPROPERTY(SaveGame)
    bool bUnlocked = false;

    UPROPERTY(SaveGame)
    bool bFirstCleared = false;  // 首次完成

    UPROPERTY(SaveGame)
    bool bAssistedCleared = false;  // 辅助完成（跳关）

    UPROPERTY(SaveGame)
    float BestClearTime = 0.0f;

    UPROPERTY(SaveGame)
    int32 ClearCount = 0;
};
```

### 决策7：存档同步到PlayerState

**问题：** 如何在联机模式同步存档数据？

**结论：** 只复制"其他玩家需要看到"的属性，不维护SaveGame指针。

**方案：**
```cpp
class AShootPlayerState : public APlayerState
{
public:
    // 可复制的存档属性（其他玩家需要看到的）
    UPROPERTY(Replicated, ReplicatedUsing=OnRep_CharacterLevel)
    int32 CharacterLevel;

    UPROPERTY(Replicated, ReplicatedUsing=OnRep_CharacterXP)
    int32 CharacterXP;

    UPROPERTY(Replicated, ReplicatedUsing=OnRep_CharacterGender)
    ECharacterGender CharacterGender;

    UPROPERTY(Replicated)
    FString CharacterName;

    // 不可复制的本地属性（技能树、剧情进度等）
    // ...

protected:
    UFUNCTION()
    void OnRep_CharacterLevel()
    {
        // 本地玩家：保存到存档
        if (IsLocalPlayerController())
        {
            SaveToSaveGame();
        }

        // 所有客户端：更新UI
        OnCharacterLevelChanged.Broadcast(CharacterLevel);
    }
};
```

**优点：**
- 不需要维护SaveGame指针
- 利用UE的属性复制系统自动同步
- 其他玩家可以看到你的角色信息（等级、装备等）
- 减少网络开销（只复制必要数据）

### 决策8：保留AI队友

**问题：** 单人模式是否需要AI队友？

**结论：** 保留。

**原因：**
1. 单人玩家体验更好（有队友可以配合、复活）
2. 技术成本不高（利用现有角色切换系统）
3. 剧情需要（双主角互动、触发剧情事件）
4. 与家园中的"另一个主角"逻辑一致

**实现：**
```cpp
void AShootGameMode::PostLogin(APlayerController* NewPlayer)
{
    Super::PostLogin(NewPlayer);

    int32 PlayerCount = GetNumPlayers();

    // 如果是单机模式且只有1个玩家，生成AI队友
    if (!IsNetworkGame() && PlayerCount == 1)
    {
        SpawnAITeammate(NewPlayer);
    }
}
```

### 决策9：不需要GameFlowSubsystem

**问题：** 是否需要一个专门的Subsystem管理地图转换？

**结论：** 不需要。

**原因：**
- UE内置的Travel机制已经足够（PlayerController::ClientTravel、GameMode::ServerTravel）
- GameFlowSubsystem只是封装了一层，没有实质性的功能增强
- 增加了一层间接性，降低了代码的可读性

**替代方案：**
- Hub → Dungeon：直接调用 `GetWorld()->ServerTravel(DungeonMapName)`
- 在线创建房间：CreateSession → ServerTravel到Lobby
- 离开游戏：DestroySession → `UGameInstance::ReturnToMainMenu()`

## 最终游戏流程

### 单人模式

```
MainMenu
  → 继续游戏（选择存档）
  → Hub（加载存档，生成AI队友）
  → 选择副本
  → 副本准备界面：单人开始
  → Dungeon
  → 完成副本
  → ReturnToMainMenu
  → 循环
```

### 本地分屏

```
MainMenu
  → 继续游戏（玩家1选择存档）
  → Hub（玩家1，单人）
  → 选择副本
  → 副本准备界面：添加本地玩家
      → CreateLocalPlayer(1)
      → 玩家2选择存档
      → 移除AI队友
  → Dungeon（分屏显示）
  → 完成副本
  → ReturnToMainMenu（移除玩家2）
```

### 在线模式

**Host流程：**
```
MainMenu
  → 继续游戏（选择存档）
  → Hub（单人，准备角色装备）
  → 选择副本
  → 副本准备界面：在线匹配 → 创建房间
      → CreateSession
      → ServerTravel到Lobby Level
  → Lobby（等待其他玩家）
      → 所有玩家"准备"
      → Host点击"开始"
  → Dungeon
  → 完成副本
  → ServerTravel回Lobby（Session保持）
      → 继续组队 / 解散队伍 → DestroySession → ReturnToMainMenu
```

**Client流程：**
```
MainMenu
  → 继续游戏（选择存档）
  → Hub（单人，准备角色装备）
  → 副本准备界面：在线匹配 → 加入房间
      → FindSessions
      → 选择房间
      → JoinSession
      → ClientTravel到Lobby Level
  → Lobby（等待Host开始）
  → Dungeon
  → 完成副本
  → ServerTravel回Lobby（Session保持）
      → 继续组队 / 离开队伍 → DestroySession → ReturnToMainMenu
```

## 地图设计

### MainMenu
- **用途：** 游戏启动后的主界面
- **GameMode：** AMainMenuGameMode
- **Session：** 无
- **功能：** 新游戏、继续游戏、角色定制、设置、退出

### Hub（家园）
- **用途：** 单人模式的核心准备区域
- **GameMode：** AHubGameMode
- **Session：** 无
- **特点：** bAllowCharacterSwitch = true
- **功能：** 自由探索、角色切换、与AI主角互动、购买装备、选择副本
- **限制：** 本地分屏和在线模式不能进入

### Lobby（匹配大厅）
- **用途：** 在线模式的等待和准备区域
- **GameMode：** ALobbyGameMode
- **Session：** Host的CreateSession
- **特点：** 必须是Level（支持ServerTravel返回）
- **功能：** 显示队友、准备状态、Host选择副本和难度
- **设计：** 小的封闭3D空间（电梯、飞机、作战室）

### Dungeon（副本）
- **用途：** 实际游戏关卡
- **GameMode：** AShootGameMode
- **Session：** 继承（如果有）
- **特点：** bAllowCharacterSwitch = false（默认）
- **功能：** 战斗、探索、任务目标、敌人生成

### 3. Session管理

**CreateSession：**
```cpp
void CreateOnlineSession(FName DungeonID, EDungeonDifficulty Difficulty)
{
    IOnlineSessionPtr Session = OnlineSubsystem->GetSessionInterface();

    FOnlineSessionSettings SessionSettings;
    SessionSettings.NumPublicConnections = 4;
    SessionSettings.bIsLANMatch = false;
    SessionSettings.bUsesPresence = true;
    SessionSettings.bAllowJoinInProgress = false;
    SessionSettings.bShouldAdvertise = true;

    SessionSettings.Set(FName("DungeonID"), DungeonID.ToString(), ...);
    SessionSettings.Set(FName("Difficulty"), (int32)Difficulty, ...);

    Session->OnCreateSessionCompleteDelegates.AddUObject(...);
    Session->CreateSession(0, NAME_GameSession, SessionSettings);
}
```

**DestroySession（Client）：**
```cpp
void ULobbyWidget::OnClientLeaveButtonClicked()
{
    IOnlineSessionPtr Session = OnlineSubsystem->GetSessionInterface();
    Session->OnDestroySessionCompleteDelegates.AddUObject(...);
    Session->DestroySession(NAME_GameSession);
}

void OnDestroySessionComplete(FName SessionName, bool bSuccess)
{
    UGameInstance* GI = GetGameInstance();
    GI->ReturnToMainMenu();
}
```

**DestroySession（Host）：**
```cpp
void ULobbyWidget::OnHostDisbandButtonClicked()
{
    // 通知所有客户端
    for (FConstPlayerControllerIterator It = GetWorld()->GetPlayerControllerIterator(); It; ++It)
    {
        APlayerController* PC = It->Get();
        if (PC && !PC->IsLocalController())
        {
            PC->ClientReturnToMainMenuWithTextReason(
                FText::FromString("Host disbanded the party"));
        }
    }

    // Host销毁Session
    IOnlineSessionPtr Session = OnlineSubsystem->GetSessionInterface();
    Session->OnDestroySessionCompleteDelegates.AddUObject(...);
    Session->DestroySession(NAME_GameSession);
}
```

### 4. 难度调整

```cpp
class AShootGameMode : public AGameModeBase
{
public:
    UPROPERTY(EditDefaultsOnly, Category="Difficulty")
    float DifficultyMultiplierPerPlayer = 0.3f;

    float GetDifficultyMultiplier() const
    {
        int32 PlayerCount = GetNumPlayers();
        return 1.0f + (PlayerCount - 1) * DifficultyMultiplierPerPlayer;
    }

protected:
    virtual void PostLogin(APlayerController* NewPlayer) override
    {
        Super::PostLogin(NewPlayer);
        RecalculateDifficulty();
    }

    virtual void Logout(AController* Exiting) override
    {
        Super::Logout(Exiting);
        RecalculateDifficulty();
    }

private:
    void RecalculateDifficulty()
    {
        float Multiplier = GetDifficultyMultiplier();
        OnDifficultyChanged.Broadcast(Multiplier);
    }
};
```

## 经验教训

### 1. Session生命周期是核心

设计联机游戏流程时，必须首先理解Session生命周期：
- CreateSession、DestroySession的时机
- Host和Client的行为差异
- 什么时候需要ServerTravel，什么时候需要ReturnToMainMenu

### 2. Seamless Travel vs Hard Travel的影响

- Seamless Travel保持PlayerController、PlayerState、ASC
- Hard Travel重建所有对象
- 设计流程时必须考虑这个差异

### 3. 不要过度设计

- GameFlowSubsystem看起来很"专业"，但实际上只是封装了UE内置的Travel机制
- 简单的问题用简单的方案，不要为了抽象而抽象

### 4. 技术限制决定设计

- "离开Lobby必须回MainMenu"是UE的技术限制
- 不要试图设计"理想的"流程，而是要设计"可实现的"流程

### 5. 统一架构的价值

- 用Listen Server架构统一单机、分屏、在线三种模式
- 大幅减少代码复杂度
- 提高可维护性
