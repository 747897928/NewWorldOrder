## 核心概念：GAS 预测机制

### PredictionKey 与 ScopedPredictionWindow

GAS (Gameplay Ability System) 的预测基于 `PredictionKey` 机制，而非手动管理预测变量。

核心流程：

1. 客户端激活 GameplayAbility 时生成 `Activation Prediction Key`
2. 客户端将 PredictionKey 发送到服务器（CallServerTryActivateAbility）
3. 客户端在 PredictionKey 有效期内应用的所有 GameplayEffect 都标记该 Key
4. 服务器接收 PredictionKey，执行 Ability，应用 GameplayEffect（也标记该 Key）
5. 服务器将 PredictionKey 同步回客户端
6. 客户端接收服务器的 GameplayEffect 时：
   - 如果 PredictionKey 匹配 → 预测正确，移除本地预测版本
   - 如果 PredictionKey 不匹配 → 预测错误，回滚

来源：GASDocumentation_Chinese/README.md 4.10 节

### GAS 可预测的内容

根据 `GameplayPrediction.h` 和 GAS 文档：

可预测：
- Ability 激活
- 触发事件
- GameplayEffect 应用（Attribute 修改、GameplayTag 修改）
- GameplayCue 事件
- 蒙太奇
- 移动（UCharacterMovement）

不可预测：
- GameplayEffect 移除
- GameplayEffect 周期效果（DoT）

重要：Instant GameplayEffect（如 Cost GE）可以预测，但预测修改其他 Character 的 Attribute 会显示短暂异常

## Lyra 的实际实现

### 重要发现：Lyra 不使用 PreReplication 机制

经过对 Lyra 源码的仔细分析，发现以下事实：

1. LyraInventoryItemInstance 没有 PreReplication 方法
2. LyraAbilityCost_ItemTagStack::ApplyCost 只在服务器执行
3. Lyra 不使用 IsFiring Tag 控制复制
4. Lyra 完全依赖 GAS 的 PredictionKey 机制

### Lyra 的真实代码

LyraAbilityCost_ItemTagStack.cpp:
```cpp
bool ULyraAbilityCost_ItemTagStack::CheckCost(...) const
{
    if (const ULyraGameplayAbility_FromEquipment* EquipmentAbility = Cast<...>(Ability))
    {
        if (ULyraInventoryItemInstance* ItemInstance = EquipmentAbility->GetAssociatedItem())
        {
            const int32 NumStacks = FMath::TruncToInt(Quantity.GetValueAtLevel(AbilityLevel));
            // 直接读取复制的 StatTags 值
            return ItemInstance->GetStatTagStackCount(Tag) >= NumStacks;
        }
    }
    return false;
}

void ULyraAbilityCost_ItemTagStack::ApplyCost(...)
{
    // 重点：仅在服务器执行
    if (ActorInfo->IsNetAuthority())
    {
        ItemInstance->RemoveStatTagStack(Tag, NumStacks);
    }
    // 客户端不执行任何操作
}
```

LyraGameplayAbility_RangedWeapon.cpp:
```cpp
void ULyraGameplayAbility_RangedWeapon::OnTargetDataReadyCallback(...)
{
    // 打开预测窗口
    FScopedPredictionWindow ScopedPrediction(MyAbilityComponent);

    // CommitAbility 会调用所有 Cost 的 CheckCost 和 ApplyCost
    if (bIsTargetDataValid && CommitAbility(CurrentSpecHandle, CurrentActorInfo, CurrentActivationInfo))
    {
        // 预测成功，继续执行
        ULyraRangedWeaponInstance* WeaponData = GetWeaponInstance();
        WeaponData->AddSpread();
        OnRangedWeaponTargetDataReady(LocalTargetDataHandle);
    }
}
```

### 本项目当前实现对照

- 成本扣减：`UShootAbilityCost_ItemTagStack::ApplyCost` 仅在服务器执行，客户端只读复制的 StatTags
- 弹药成本：`UShootAbilityCost_AmmoTagStack` 在运行时根据 `UShootRangedWeaponInstance::GetAmmoPerShot` 设置 Quantity
- 过载状态：`UShootAbilityCost_AmmoTagStack` 检测 `Status.Overload` 时跳过弹药扣减
- 防止幽灵子弹：`UShootGameplayAbility_Weapon_Fire` 采用 `FScopedPredictionWindow` + `CallServerSetReplicatedTargetData` + `ConsumeClientReplicatedTargetData`，对 TargetData 做服务端确认
- 预测接口：`UShootRangedWeaponInstance::GetPredictedAmmo/Reserve` 当前返回权威值，仅保留蓝图兼容

### Lyra 的预测流程

T=0.0s  客户端激活 Ability
        → 生成 PredictionKey
        → 打开 FScopedPredictionWindow
        → CheckCost：读取当前 StatTags（30发） → 通过
        → ApplyCost：客户端不执行（!IsNetAuthority）
        → UI 仍显示 30 发 ⚠️ 客户端没有即时反馈

T=0.075s 服务器执行 Ability
         → CheckCost：读取 StatTags（30发） → 通过
         → ApplyCost：服务器扣减 30 → 29
         → StatTags 开始复制到客户端

T=0.15s 客户端接收 StatTags 复制
        → UI 更新：30 → 29 ✅ 有延迟但正确

### Lyra 方案的特点

优点：
- 完全依赖 GAS 预测，无需手动管理
- 代码简洁，无条件复制逻辑
- 服务器权威，防作弊

缺点：
- 客户端 UI 更新有网络延迟（通常 50-150ms）
- 高射速武器连射时 UI 会"跳跃"更新
- 单机游戏也会有延迟（因为走的是复制流程）

## 常见误解与纠正

### 误解 1：Lyra 使用 PreReplication + IsFiring Tag

来源：网上一些文章声称 "Lyra uses PreReplication to disable ammo replication during firing"

真相：Lyra 源码中完全没有这段代码。可能是某些作者的设想或第三方实现。

### 误解 2：FastArray 的 PreReplicatedRemove 用于预测

来源：看到 GameplayTagStackContainer 的 PreReplicatedRemove 回调

真相：这些回调仅用于更新本地 TagToCountMap，不是预测机制：

GameplayTagStack.cpp:
```cpp
void FGameplayTagStackContainer::PreReplicatedRemove(const TArrayView<int32> RemovedIndices, int32 FinalSize)
{
    // 仅更新本地容器，复制已经发生
    for (int32 Index : RemovedIndices)
    {
        const FGameplayTag Tag = Stacks[Index].Tag;
        TagToCountMap.Remove(Tag);
    }
}
```

### 误解 3：GAS 不能预测 StatTags 修改

来源：GAS 文档说 "不能预测 GameplayEffect 移除"

真相：
- StatTags 不是通过 GameplayEffect 修改的（直接调用 AddStack/RemoveStack）
- 可以预测，但 Lyra 选择不预测（只在服务器修改）
- 如果要预测，需要手动管理（如ARangedWeaponInstance 的 PredictedAmmo）

## 实现方案对比

### 方案 A：Lyra 原始方案（StatTags + 服务器修改）

实现：
```cpp
// CheckCost：客户端和服务器都读取复制的 StatTags
bool CheckCost() const
{
    return ItemInstance->GetStatTagStackCount(AmmoTag) >= Cost;
}

// ApplyCost：仅服务器修改
void ApplyCost()
{
    if (ActorInfo->IsNetAuthority())
    {
        ItemInstance->RemoveStatTagStack(AmmoTag, Cost);
    }
}
```

特点：
- UI 更新延迟 = 网络延迟（50-150ms）
- 代码简洁，完全依赖 GAS 预测
- Epic 官方方案，稳定可靠

适用：
- 单次射击武器（手枪、狙击枪）
- 低射速武器（步枪、霰弹枪）
- 可以接受轻微 UI 延迟的游戏

### 方案 B：手动预测（PredictedAmmo + CurrentAmmo）

实现（项目现有 ARangedWeaponInstance）：
```cpp
// 服务器权威值
UPROPERTY(ReplicatedUsing=OnRep_CurrentAmmo)
int32 CurrentAmmo;

// 客户端预测值
UPROPERTY(Transient)
int32 PredictedAmmo;

// CheckCost：客户端读预测值，服务器读权威值
bool CheckCost() const
{
    int32 Ammo = HasAuthority() ? CurrentAmmo : PredictedAmmo;
    return Ammo >= Cost;
}

// ApplyCost
void ApplyCost()
{
    if (HasAuthority())
    {
        CurrentAmmo -= Cost;  // 服务器修改权威值
    }
    else
    {
        PredictedAmmo -= Cost;  // 客户端修改预测值
    }
}

// 复制回调：同步预测值
void OnRep_CurrentAmmo()
{
    PredictedAmmo = CurrentAmmo;
}
```

特点：
- UI 更新即时（无延迟）
- 需要手动管理预测和同步
- 代码复杂度中等

适用：
- 高射速武器（机枪、突击步枪）
- 需要即时 UI 反馈的游戏
- 单机模式也需要即时反馈

### 方案 C：PreReplication + IsFiring Tag（不推荐）

实现（本文档之前错误描述的方案）：
```cpp
void UShootInventoryItemInstance::PreReplication(...)
{
    const bool bIsFiring = ASC->HasMatchingGameplayTag(Tag_IsFiring);
    DOREPLIFETIME_ACTIVE_OVERRIDE(ThisClass, StatTags, !bIsFiring);
}
```

问题：
- Lyra 并未采用此方案
- 需要在两端都执行 RemoveStatTagStack（客户端 + 服务器）
- 容易产生同步问题
- PreReplication 每帧调用，性能开销
- 停火后需要额外逻辑确保同步

不推荐原因：
- 过度设计，增加复杂度
- Lyra 未验证，稳定性未知
- 已有更简单的方案（A 或 B）

## 推荐实现路径

### 路径 1：采用 Lyra 方案（当前项目已采用）

步骤：

1. 使用 `UShootAbilityCost_ItemTagStack`（已落地）
```cpp
// ShootAbilityCost_ItemTagStack.h/cpp
// 完全照搬 LyraAbilityCost_ItemTagStack 的实现
```

2. 武器 Ability 使用 `UShootAbilityCost_AmmoTagStack` 配置 Tag 与 Quantity

3. CommitAbility 时自动处理

优点：代码简洁，Epic 验证
缺点：UI 有轻微延迟

### 路径 2：可选预测方案（未落地）

如需 UI 即时反馈，可在 `UShootRangedWeaponInstance` 增加预测字段并同步：

步骤：

1. 在 UShootRangedWeaponInstance 添加预测字段
```cpp
UCLASS()
class UShootRangedWeaponInstance : public UShootWeaponInstance
{
    UPROPERTY(Transient)
    int32 PredictedAmmoInMag = 0;

    UPROPERTY(Transient)
    int32 PredictedReserveAmmo = 0;
};
```

2. CheckCost 读取预测值（示例仅示意）
```cpp
bool UShootAbilityCost_AmmoTagStack::CheckCost() const
{
    UShootRangedWeaponInstance* Weapon = GetWeaponInstance(Ability);
    UShootInventoryItemInstance* Item = GetItemInstance(Weapon);

    int32 MagAmmo, ReserveAmmo;
    if (Ability->GetCurrentActorInfo()->IsNetAuthority())
    {
        // 服务器：读 StatTags 权威值
        MagAmmo = Item->GetStatTagStackCount(Tag_Ammo_Magazine);
        ReserveAmmo = Item->GetStatTagStackCount(Tag_Ammo_Reserve);
    }
    else
    {
        // 客户端：读预测值
        MagAmmo = Weapon->GetPredictedAmmoInMag();
        ReserveAmmo = Weapon->GetPredictedReserveAmmo();
    }

    return MagAmmo >= Cost;
}
```

3. ApplyCost 分离客户端和服务器逻辑
```cpp
void UShootAbilityCost_AmmoTagStack::ApplyCost()
{
    UShootRangedWeaponInstance* Weapon = GetWeaponInstance(Ability);
    UShootInventoryItemInstance* Item = GetItemInstance(Weapon);

    if (Ability->GetCurrentActorInfo()->IsNetAuthority())
    {
        // 服务器：修改 StatTags
        Item->RemoveStatTagStack(Tag_Ammo_Magazine, Cost);
    }
    else
    {
        // 客户端：修改预测值
        Weapon->ConsumeAmmoPredicted(Cost);
    }
}
```

4. 复制回调同步预测值（示例）
```cpp
// UShootInventoryItemInstance.cpp
void UShootInventoryItemInstance::OnRep_StatTags()
{
    // 同步到 WeaponInstance 的预测值
    if (UShootRangedWeaponInstance* Weapon = GetCurrentWeaponInstance())
    {
        Weapon->SyncPredictedFromStatTags(this);
    }
}
```

优点：
- UI 即时反馈
- 适配现有代码
- 保留特殊武器支持（霰弹枪每发装弹）

缺点：
- 需要手动管理预测
- 代码复杂度略高
